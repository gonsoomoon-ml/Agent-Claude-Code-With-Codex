## 1. 목표·비목표·반목표

**목표**
1. 검증 AI 후보 5종 중 운영에 쓸 모델을 정확도·비용·지연으로 고른다. 후보는 GPT-6 Astra·Sol·6.1 Sol·Luna 와 GPT-5.5 기준선이다.
2. 요약 AI 조건 6가지(A0–A5)를 같은 지시·같은 기사로 비교해 업그레이드 조합(CLI·모델·effort)을 고른다.
3. 업그레이드 전후 비용을 실측값으로 비교한다. 운영 기록의 검증 비용 고정 추정치($0.032/claim)를 대체한다.
4. 결과를 리포트로 남기고, 승인되면 한 번에 하나씩 배포한다.

**비목표**
- 요약 지시(프롬프트) 변경. S1–S5 는 업그레이드 뒤 별도로 한다.
- 관련성 판정(Haiku) 모델 평가. U8 4단계(선택)에서 따로 한다.
- 알려진 버그 수정(F1·F2·F4)과 원문 상한 재검토(F6).

**반목표** — 기술적으로 돌아가도 실패로 본다.
- 실험이 운영 DynamoDB(카드 캐시·원장·원문 저장소)에 쓴다.
- 로컬 실행에 사용자 설정·플러그인이 섞여, 운영과 다른 조건으로 잰다.
- 모델 차이와 effort 차이가 섞인다.
- 처리 시간을 동시 실행 중에 잰다.
- 판정자가 요약 AI 와 같은 계열(Claude)이다.
- 확인하지 않은 가격을 사실처럼 리포트에 쓴다.
- `deploy_scheduler` 를 다시 실행한다.

## 2. 제약 (비협상)

- **실행 격리**
  - 요약 AI(`claude -p`)와 검증 AI(`codex exec`)는 빈 작업 디렉토리에서, stdin 을 닫고 실행한다.
  - 검증 AI 에는 envelope 4필드(원문·claim·claim_type·schema) 외에 아무것도 주지 않는다.
- **호스트 오염 차단**
  - 로컬 `claude -p` 는 사용자 설정과 플러그인이 없는 빈 `HOME` 으로 실행한다. 2026-10-16 프로브에서, 그대로 돌리면 사용자 플러그인 훅 2개와 도구 72개가 실려 입력이 70,289 토큰이었다.
  - 빈 `HOME` 에서는 `~/.aws` 가 보이지 않는다. 이 호스트의 자격 증명은 `~/.aws/credentials`(shared-credentials-file)에서 오고, 기본 리전은 us-west-2 다. 따라서 `AWS_SHARED_CREDENTIALS_FILE`·`AWS_CONFIG_FILE` 를 실제 경로로, `AWS_REGION=us-east-1` 로 지정한다.
- **운영 데이터 보호**
  - 운영 DynamoDB 는 읽기만 한다(`briefing-source-store`·`briefing-card-cache`·`briefing-ledger`).
  - 실험은 `BACKEND=local` 저장소만 쓴다.
- **저작권:** 원문 사본은 저장소 밖 실험 디렉토리에만 두고 커밋하지 않는다.
- **설정 관리:** 모델 id 와 effort 는 `.env` 에서 사용자가 직접 관리한다. 배포 때는 바꿀 줄을 안내한다.
- **배포**
  - `deploy_runtime` 만 쓴다. `deploy_scheduler` 를 다시 실행하면 `BRIEFING_DRY_RUN=1`(실제 발송이 꺼지는 시험 모드)로 리셋된다.
  - 발송 시간(05:00 KST) 앞뒤는 피한다.
- **승인:** 저장소 파일을 바꾸는 구현은 이 문서와 실행 계획이 승인된 뒤에 한다.

## 4. 실험 환경

- **실험 디렉토리:** `~/upgrade-eval/`. 저장소 밖이고 영구 보존한다.

- **CLI 설치:** 호스트 전역 설치와 운영 설정은 건드리지 않는다.

  - codex 0.142.2 와 0.163.0 도 각각 prefix 에 설치한다. codex 마다 전용 설정 디렉토리(`CODEX_HOME`)를 두고, 운영 컨테이너와 같은 방식으로 `codex_config.toml`(모델·effort 만 바꿈)을 넣는다.

## 6. Stage B — 검증 AI 비교 (U3)

- **후보:** `openai.gpt-6-astra`·`openai.gpt-6-sol`·`openai.gpt-6.1-sol`·`openai.gpt-6-luna`(codex 0.163.0), `openai.gpt-5.5`(codex 0.142.2, 운영과 같음).
- **claim 세트**
  - **원본:** 12건 운영 카드의 함의 claim. 숫자가 든 claim 은 `reroute_claim_types` 규칙대로 Python 경로라서 뺀다. 약 80–100개.
  - **심은 오류:** 원본에서 약 40개를 골라 6가지 유형으로 바꾼다(유형별 6–8개).
    - 유형: 주체 바꾸기, 유보→단정, 단계 격상(프리뷰→출시), 귀속 삭제, 의미 반전, 원문에 없는 사실 추가.
    - 작성자는 설계자(Claude)이고 `planted` 라벨을 붙인다. 숫자 변경은 Python 경로라 넣지 않는다.
  - **정답**
    - 심은 오류는 VERIFIED 가 아니면 '잡았다'로 본다. 그중 BLOCKED 로 잡은 비율도 따로 보고한다.
    - 원본은 5개 모델 중 4개 이상이 VERIFIED 면 '맞는 claim'으로 본다. 그 밖은 '불확실'로 분류해 오탐 계산에서 빼고 목록으로 보고한다.
  - **오탐 정의(설계자 결정):** 맞는 claim 을 VERIFIED 로 판정하지 못한 비율이다. BLOCKED 와 DEMOTED 를 모두 넣고, 둘을 따로도 보고한다.
    - BLOCKED 만 세면, 모두 DEMOTED 로 판정하는 모델이 오류는 다 잡고 오탐은 0 이 되어 이겨 버린다.
    - 운영에서 DEMOTED 는 '미확인' 표시로 발행되고, BLOCKED 는 다시 쓰기 후 드롭 또는 보류로 이어진다.
- **실행**
  - 모델마다 전체 세트를 2회, 순서를 무작위로 돌린다(병렬 가능).
  - 처리 시간은 모델마다 원본 30개를 순서대로 1회 돌린 값으로 잰다.
- **effort:** 모든 모델에 같은 값을 `model_reasoning_effort` 로 명시한다. 운영은 이 값을 설정하지 않아 codex 기본값으로 돈다. 시작 전에 0.142.2 의 기본값을 확인해 그 값으로 통일한다.
- **호출마다 기록:** 판정, 근거, 토큰 4종, 지연, 종료 코드, 시간 초과(120초), codex 버전, effort.
- **승자 규칙** (설계자의 판단, 조정 가능)
  1. 심은 오류 검출률이 최고 모델과 5%p 이내이면서 GPT-5.5 이상인 모델만 후보로 남긴다.
  2. 그중 오탐률(맞는 claim 을 막은 비율)이 낮은 순으로 본다.
  3. 차이가 2%p 이내로 비슷하면 claim 당 비용과 처리 시간 p95 가 낮은 쪽을 고른다.
  - 2회 판정 일치율이 90% 미만이면 리포트에 경고를 단다.
- **비용(추정):** 약 $50–60.
- **재승인 지점(§14-2):** Stage B 가 끝나면 멈춘다. 승자 실측 단가로 Stage A 검증 비용과 판정 비용을 다시 계산해 보고하고, 승인받은 뒤 Stage A 를 시작한다.

- **effort 표기의 근거:** A0·A1 의 실제 effort 는 출력(envelope)에 나타나지 않는다. 리서치가 인용한 vendor 문서에 따르면 Sonnet 5 의 기본값은 high 이고 5.5 계열은 medium 이다(관측한 값은 아니다).
- **규모:** 6 × 12건 × 3회 = 216회.
- **실행 경로:** 운영 `produce_card` 를 그대로 쓴다. 초안 → 검증 → 실패하면 1회 다시 쓰기 → 발행 또는 보류. 지시는 v3.4, 사용자는 `_FACT_USER`(general, skill 없음).
- **검증 AI:** Stage B 승자를 실험 codex 러너와 같은 effort 로 쓴다.
- **처리 시간:** 조건마다 반복 1회분(12건)을 순서대로 돌려 잰다. 나머지는 병렬로 돌리되, Bedrock 제한에 대비해 동시 실행은 4개 이하로 한다.
- **시간 제한(설계자 결정):**
  - 병렬 실행은 600초로 둔다(`scripts/ab_prompt.py` 선례). 동시 실행이 처리 시간을 부풀려 운영에서는 나지 않을 시간 초과가 생기기 때문이다.
  - 운영 기준 360초 초과 여부는 순차로 돌린 1회분에서만 판정한다.
- **기록**
  - 최종 카드(요약·why·claims·판정·결정·시도 횟수)와 1차 초안 요약(DI 래퍼로 잡음)
  - 지연, `claude -p` envelope 의 `total_cost_usd`·`usage`, `stop_reason`
  - 오류: 시간 초과(360초)·응답 거절·JSON 파싱 실패·max_tokens 중단
  - 모델 id, CLI 버전, 설정한 effort
- **비용(추정):** 요약 약 $30–40, 여기에 검증(승자 단가 × claim 수)이 더해진다.

## 8. 판정 파이프라인 (U5, 전체 채점)

- **판정자** (모두 Bedrock Converse)
  - GPT-6 Astra(`us.openai.gpt-6-astra`), GPT-6.1 Sol(`global.openai.gpt-6.1-sol`). 둘 다 2026-10-16 에 Converse 호출을 확인했다.
  - 제3계열 후보: xAI Grok 4.7, Moonshot Kimi K3, Z.ai GLM 5.3, Amazon Nova Premier. 정확한 id 는 `list-inference-profiles` 에서 확인한다.

    - Astra 가 이기면: 6.1 Sol 이 주 판정, 제3계열이 교차 판정.
    - 6.1 Sol 이 이기면: Astra 가 주 판정, 제3계열이 교차 판정.

1. **판정자 검증(결함 심기)**
   - A0 요약 12개(반복 1회분)에 결함 6유형을 심은 요약 약 36개를 만들고, 원본 12개와 섞는다.
   - 결함 유형: 유보 삭제, 숫자 변경, 단계 격상, 귀속 삭제, 인용 변형, 뒤쪽 핵심 사실 삭제.
   - 판정자마다 검출률과 오탐률을 잰다.
   - 기준(설계자의 판단, 조정 가능): 검출률 80% 이상, 오탐률 10% 이하. 미달 판정자는 빼고 리포트에 기록한다.
   - **세는 단위(설계자 결정):**
     - 검출률은 심은 결함 하나 단위로 센다.
     - 오탐률은 결함을 심지 않은 문장 단위로 센다.
     - 원본 요약에 실제 결함이 있을 수 있으므로, 원본에 대한 지적은 바로 오탐으로 세지 않는다. 제3계열과 설계자가 원문 근거로 확인해 맞는 지적이면 오탐에서 뺀다.
   - **미달 시(설계자 결정):**
     - Astra 가 미달이면, 통과한 다른 판정자(6.1 Sol 또는 제3계열 최고)로 주 판정을 바꾼다.
     - GPT 판정자 둘 다 미달이면 채점(~$100)을 시작하지 않고 사용자에게 보고해 다시 승인받는다.
   - 제3계열은 이 시험에서 가장 높은 모델로 고른다.
2. **핵심 사실 목록**
   - 12건마다 Astra 가 요약을 보기 전에 원문에서 핵심 사실을 뽑는다.
   - 사실마다 기록할 것: 위치(원문 내 문자 오프셋 ÷ 길이로 앞·중·뒤 3분위), 범주(① 새 사실·주체 ② 수치 ③ 변화 ④ 단서·반론, 배경, 발언), AI 관련 여부.
   - 6.1 Sol 은 목록을 검토만 한다(빠진 것, 잘못 나눈 것 표시).
   - 사람이 3건을 확인한다(D2).
3. **채점:** 216개 전부, 판정자 2개가 맡는다.
   - **Q1 중요한 걸 담았나**
     - 핵심 사실과 요약을 맞춰 커버리지를 구한다(전체, 위치별, 범주별, 문장당).
     - 기준 1: 첫 문장이 ①(새 사실)인지 예/아니오로 판정한다. 제목 반복 여부는 코드로 본다(제목과 첫 문장의 토큰 겹침).
     - 기준 3: AI 관련 핵심 사실의 커버리지를 본다.
   - **Q2 원문대로 말했나**
     - 문장마다 라벨을 붙이고 근거가 되는 원문 구절을 함께 남긴다.
     - 라벨: 부풀림(범위·단계·한정어·인과·권고·확신도), 지나친 흐림, 귀속 누락, 의견→사실, 인용 불일치.
     - 인용 대조는 코드로 한다. 따옴표 안 문구가 원문의 부분 문자열인지 본다.
   - **Q3 검증이 다 덮나**
     - 요약 사실 중 claim 이 없는 것의 비율을 구한다. 숫자는 `numeric.scan`, 라틴 이름은 정규식(코드)으로, 나머지는 판정자가 본다.
     - 1차 통과율은 실행 로그에서 구한다.
   - **Q4 형식·비용** — 모두 코드로 잰다.
     - 문장 수('다.' 기준), 150자 초과 문장 비율
     - 유보 보존(`scripts/ab_prompt.py` 의 `_HEDGE`), 최심 위치(`_depth`, 보조 지표)
     - 이름 원어 표기(정규식), claim 수, 지연, 비용
   - **Q5 (참고용)**
     - A1–A5 를 각각 A0 와 짝짓는다. 같은 기사의 반복 3회 중 중간 길이 요약끼리다.
     - 순서를 바꿔 2회 묻고, 판정자 2개가 모두 판정한다.
   - **갈린 경우:** Q1 정렬이나 Q2 라벨에서 판정자 둘이 갈리면 제3계열이 가린다. 사람 확인 8–12개는 갈린 항목에서 무작위로 고른다.
4. **집계와 결론**
   - **채점 대상(설계자 결정)**
     - 품질은 최종 카드(운영 발행물과 같은 것)로 채점한다.
     - 보류(QUARANTINE)·시간 초과·오류로 발행되지 않은 실행은 품질 채점에서 빼고 '발행 실패율'로 따로 센다.
     - 보류 중 알려진 F2 표기(숫자 없는 per million, triple·double, decades, N위·N분기 서수, 만 혼합 표기)로 막힌 것은 표시한다. 결정에는 F2 를 뺀 보류율을 쓰고, 원래 값도 함께 보고한다. F2 는 고칠 예정이기 때문이다.
     - 사실층 '왜 중요한가' 칸에 요약·claim 에 없는 수치가 있는지 코드로 센다. 비용이 거의 없어 함께 잰다.
   - 기사 단위로 짝지어 비교하고, 기사를 재표집하는 부트스트랩(10,000회)으로 95% 신뢰구간을 구한다.
   - '차이 없음'은 신뢰구간이 0 을 포함하거나, 차이가 같은 조건 3회 반복 사이 표준편차보다 작은 경우다.
   - 결정 순서: 안전(검증 우회율, 인용 불일치, 발행 실패율) → 충실도(Q2) → 담은 양(Q1) → 비용·속도.
     - 기준선(A0)보다 안전이나 충실도가 나빠진 조건은 탈락한다.
     - 발행 실패율은 A0 보다 5%p 이상 높으면 탈락한다(설계자 결정, 조정 가능).
   - 설계자(Opus 5.5)는 후보와 같은 계열이라 점수를 매기지 않고 사례 모음만 정리한다.

   - 그 밖이면: D3 그대로.
4. **다른 작업과의 배포 순서 — 보류.**
   - `deploy_runtime` 은 작업 트리에서 빌드하는데, 작업 트리에 헤드라인·카탈로그 작업의 미커밋 변경이 있다.
   - 정해질 때까지 배포(F3·F7·U8)는 하지 않는다.
   - 실험(U2–U7)은 운영 커밋에 고정한 worktree 에서 돌리므로 진행할 수 있다.
